## Core question

The educational value of this recipe lies in its glue code: how do file operations, tool results, and verifier outcomes in a Harbor trial become the `prompt_token_ids / response_ids / loss_masks / rollout_logprobs / rewards` required by SkyRL? Beyond the training formulas, failure classification and tokenizer boundaries can both change the learning signal.

`TITOHarborFullyAsyncExp.get_trainer()` returns the external SkyRL `FullyAsyncRayPPOTrainer`; the recipe supplies `TITOHarborGenerator`. The generator runs trials concurrently for each input task path and trajectory id. Tasks can run concurrently, but actual starts are controlled by a rate limiter. `_run_tito_trial()` configures the session/cache salt, runs a Harbor Trial, reads the verifier reward and agent metadata, and converts them into `GeneratorOutput`.

On the agent side, `TITOAgentState` maintains three parallel arrays. `record_step()` first saves a snapshot of this turn's input tokens, then directly appends sampled tokens, mask=1, and actual logprobs. Tool observations are generated through chat-template deltas against a fixed dummy base and appended with mask=0 and logprob placeholders. Stop-token overlap must be handled according to template boundaries such as GLM/ChatML to avoid duplicate tokens or missing newlines.

The generator splits the initial prompt from the response region at the first mask=1 position. The response can still contain tool/environment tokens with mask=0. Thus, `response_ids` does not mean that every token was generated by the model.

## Confirmed mechanisms and tradeoffs

- **Implementation fact:** Fixed-base tokenization does not retokenize the full history, reducing history processing that grows with the number of turns. The O(1) in the comment should be understood relative to the number of historical turns, not as constant time with respect to the length of tool-observation text. This method depends on template conventions and cannot be generalized to arbitrary tokenizers without testing.
- **Implementation fact:** The current cache-salt implementation takes `weight_version`, asserts that it exists, and returns `weight_version=...`; it is not global_step, and it does not concatenate the model name into the string as the docstring describes. The source is more specific than the comment. Under asynchronous execution, policy version and step need not advance together.
- **Implementation fact:** Per-turn `length` truncation forces reward=0 and takes precedence over context-length; the latter zeros the loss mask when overlong filtering is enabled. Timeouts, environment errors, and getting the task wrong are different kinds of negative samples.
- **Implementation fact:** Any non-timeout error within the same instance masks the entire group. By default, timeouts mask the entire group when they reach the threshold of 2; otherwise, only the timed-out members are masked. The policy groups by `trajectory_id.instance_id`, not by return time. Zeroing error cases must not be described as teaching the model to learn from environment failures.
- **Implementation fact:** Session slots are released in finally; each retry uses a new session id. e2e timing excludes the initial rate-limiter wait but includes time between retries, so it cannot be directly compared with metrics that include queueing latency.
- **Reading assessment:** These local policies determine selection bias in the effective training data. Before reproducing reward curves, reproduce the definitions used to count errors, timeouts, and valid tokens.
