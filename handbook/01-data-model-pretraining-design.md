# 01｜从能力目标到可交付基础模型：数据、架构与预训练设计

[返回全流程](00-end-to-end.md) · [分布式执行](02-distributed-pretraining-operations.md) · [Marin 535B 案例](04-marin-535b-live-case-study.md)

核查日期：2026-09-08。本章讨论从随机初始化权重开始、最终交付可供后训练使用的基础模型。复用公开 tokenizer、数据处理器或训练框架仍属于从头训练；载入已有模型权重继续训练则属于续训。本地工作仅阅读源码、配置与公开报告，没有下载训练语料或模型权重，没有执行实验。

证据分三类：**【公开事实】**指作者报告或已定位实现；**【综合设计】**指把不同项目经验连接成的工程流程，不代表任何一家实验室的完整配方；**【未知】**指公开资料不足以确认的闭源前沿细节。各阶段的 Gate 是建议的验收条件，具体阈值须在项目启动时登记，不能把本文当作通用超参数表。

**当前规模的参照。**【公开事实】Open Athena 在 2026-09-03 披露，Marin 已启动一个总参数 535B、每 token 激活参数 23B 的 MoE 训练，计划约三个月、18T tokens。公告描述的是进行中的运行，不能据此声称模型已完成、达到某个评测成绩，或把预计训练时间作为实测成本。[Marin 535B-A23B 启动说明](https://openathena.ai/blog/marin-535b-launch-note/)

## Gate 0：先确定要买到的能力，再分配训练预算

**输入：**目标使用场景、部署预算、可获得的数据与计算资源。**输出：**能力矩阵、冻结的评估协议、资源预算，以及候选模型范围。

【综合设计】将“强模型”拆成语言覆盖、代码、数学、知识、长文档理解、工具使用前置能力等目标；每项写清测量方式、最低接受水平与不能牺牲的能力。基础模型评估可以使用补全、似然和受控少样本任务；需要 SFT 才能稳定表现的聊天行为应另设诊断，避免把不会遵循模板误判成没有知识。评估集要隔离于训练与数据筛选，记录版本、提示格式、采样和聚合方法。

预算至少拆成数据处理、探索实验、主训练、恢复与返工、评估，以及后训练与推理验证。给定 GPU 数量并不等于给定有效算力：网络、存储、停机、上下文长度和模型形状都会改变可完成的 token 数。先用候选实现测量稳定吞吐，再估算墙钟时间，并为不可用时间留出明确预算。部署端同时约束权重驻留、KV cache、首 token 延迟和每次任务总消耗；训练最省算力的模型不一定是全生命周期成本最低的模型。

【公开事实】Chinchilla 研究在其训练设置中研究模型参数与训练数据的计算最优分配。常用的稠密 Transformer 粗估 `C ≈ 6 × N × D` 可帮助构建第一版预算；其中 `N` 的计数口径必须明确，且该近似省略或简化了注意力等成本。它不能推出所有时代、数据质量、训练长度和服务目标都适用固定 tokens/parameter 比例。[Chinchilla 原始论文](https://arxiv.org/abs/2203.15556)

**权衡与故障信号：**预算只覆盖主训练却没有验证和恢复空间；目标上下文使吞吐远低于估算；训练成本合格但无法按目标延迟部署。**通过条件：**至少有一个候选方案在保守吞吐估计下满足完整预算，并且评估协议能区分“基础知识不足”和“交互格式不匹配”。

## Gate 1：把 scaling law 当成需要验证的预测模型

**输入：**候选架构、初始数据混合、tokenizer 和预算。**输出：**可复现的 scaling recipe、留出规模上的预测误差，以及主训练前的决策记录。

【综合设计】先在小规模上筛除明显不稳定的组合，再做多个计算预算下的等算力扫描：同一预算比较较大模型加较少 tokens，与较小模型加较多 tokens。架构、优化器、初始化、批量及学习率如何随宽度、深度和训练时长变化，本身就是被检验的假设。数据质量或混合比例的消融应尽量固定这些变量；涉及不同 tokenizer 时，不能直接比较每 token 交叉熵的绝对值。

拟合用的小规模运行与验证预测的较大规模运行必须分开。保留接近目标模型形状的短跑，检查路由、内存、通信与数值稳定；同时保留足够长的运行检查训练时长外推。短跑吞吐正常不证明数万步以后稳定，短期下降更快也不证明最终更好。下游能力应单独测量，不能用平均验证 loss 替代所有能力目标。

【公开事实】Marin 的 Delphi 公开了失败后修改配方的过程：第一次小规模拟合看似良好，却未能预测更大的运行；修订后，预先登记的预测对一个 `1e23 FLOPs` 运行的最终 loss 误差在 0.2% 内。这个结果属于其特定数据、架构和超参数迁移方案，并不是任意模型都能外推 300 倍的保证。[Delphi scaling suite 作者说明](https://openathena.ai/blog/delphi/)

**权衡与故障信号：**小模型偏好的混合在较大模型反转；延长训练才出现梯度尖峰；拟合误差很小但留出规模偏离；用同一评估集反复选择方案造成过拟合。**通过条件：**关键选择有消融证据，留出运行的误差可接受，主训练预测及触发重新设计的条件已登记。没有依据时保留不确定区间，不填入虚构的精确收益。

## Gate 2：把数据做成可追踪、可重建的训练产品

**输入：**原始网页、代码、论文/OCR、数学、长文档及必要的合成数据。**输出：**带来源记录的文档库、评估隔离清单、tokenized shards、数据混合清单和质量报告。

【综合设计】建议流水线为：来源登记 → 抽取与规范化 → 语言和领域识别 → 质量筛选 → 去重与评估去污染 → 分割和分片 → tokenization → 混合采样。顺序需要按来源调整，例如先移除网页模板能提高近似去重效果，但应保留原文标识以便追查。每一条记录至少关联来源、抓取或发布版本、许可/使用条件、原始标识、内容校验、处理代码版本、过滤原因和父记录。合成数据增加生成模型、提示、采样与验证器版本，区分新样本数量与可证实的信息增量。

质量并不等于统一分类器分数。网页需要关注导航与模板残留；代码需保持文件、仓库和依赖语境；OCR 要观察公式和版面损坏；多语种过滤需检查少数语言是否被系统性误删。高质量筛选可能改善短期学习效率，却损失覆盖面和稀有能力，因此按领域、语言和长度进行人工抽样与保留率审计。

去重要同时考虑完全重复、近似重复和来源簇。代码 fork、网页镜像、文档修订版可能跨越训练与验证边界；只对单个 shard 去重不足以处理全局重复。去污染应覆盖评估题目、答案、解说及其近似变体，并保留可追查的匹配记录。字符串相似度与语义相似度各有误报、漏报，不能把一个“零匹配”指标解释为绝对没有污染。

混合比例明确以文档数、字节还是有效 tokens 计量，并同时记录计划比例和实际采样比例。重复采样会增加训练 tokens，却不会等量增加独特信息；高权重小语料应报告有效轮数、重复程度与退化迹象。长文档池、数学和代码池可以为后续阶段预留，避免进入 midtraining 时才发现已经反复学过相同材料。

【公开事实】Marin 的 `ArtifactStep` 将配置和依赖版本纳入 fingerprint，产物地址则使用显式的名称与版本；这让数据与实验依赖可以成为图中的对象。源码没有因此保证原始数据内容及全部执行代码自动获得完整内容寻址，所以使用者仍须登记数据校验和代码 SHA。[Marin 产物身份与版本实现](https://github.com/marin-community/marin/blob/5e2436d0f61462983003bd8b6eaef8235ecab78c/lib/marin/src/marin/execution/lazy.py#L213-L237)

**权衡与故障信号：**质量分数上升但语言覆盖下降；去重后有效数据量骤减；训练和验证 loss 异常接近；实际混合偏离配置；同名数据版本产生不同内容。**通过条件：**来源可追溯、隔离和去重策略可解释、实际 tokens 分布符合设计，任一被采样训练片段能回溯到其来源与变换链。

## Gate 3：冻结 tokenizer 与模型之间的数据契约

**输入：**代表目标分布的样本和候选 tokenizer。**输出：**版本固定的 tokenizer、特殊 token 规范、词表与 embedding 形状，以及编码测试集。

【综合设计】比较语言和代码上的 token 膨胀、数字切分、字节回退、编码解码往返、特殊符号处理和词表大小。分词更短可以降低序列成本，但更大的词表增加 embedding、输出投影和优化器状态；压缩率也不能替代下游质量。不同分词器下，可补充按同一原始文本、字节口径归一化的指标及相同任务评估，说明各口径的限制。

冻结词表文件、规范化规则、BOS/EOS/PAD 的 ID 与含义，并检查 tokenizer 的文档长度配置和模型位置范围不是混为一谈。后续追加特殊 token 会影响模型形状及新行初始化，必须是显式迁移，而非无记录地替换文件。

【公开事实】OLMo-core 分开表示词表大小、EOS、PAD 和可选 BOS，并提供 `padded_vocab_size`，默认把 embedding 维度向上补至 128 的倍数以改善吞吐。补齐后的模型行数不等于新增真实词元；具体对齐值是实现选择。[OLMo tokenizer 配置](https://github.com/allenai/OLMo-core/blob/92870a33c3fee060d57c3faec52b0b369ece85a6/src/olmo_core/data/tokenizer.py#L48-L107)

**权衡与故障信号：**某语言长度异常膨胀；特殊 token 在普通内容中被误解释；PAD 与 EOS 处理冲突；数据 ID 越界。**通过条件：**边界样本和往返行为已定义，所有数据分片与模型引用同一 tokenizer 版本，指标比较口径一致。

## Gate 4：联合选择模型架构与可实现的计算形状

**输入：**能力目标、scaling 结果、训练集群和部署约束。**输出：**架构规格、参数/FLOPs/内存分解和已验证的候选系统配置。

【综合设计】Dense 的优点是执行路径和成本结构相对直接；MoE 允许增加总容量而仅计算部分专家，但须同时列出总参数、每 token 激活参数、共享层、专家数、top-k、路由方式和容量策略。用 23B 激活参数描述一个 535B MoE，不表示其权重或优化器状态只有 23B；状态如何分片、专家负载和通信怎样分布，都必须单独计算。激活参数也不能完整代表注意力、路由、数据搬运和重计算成本。

【公开事实】Megatron 路由实现支持不同路由分支，并按配置执行专家容量限制与 token dropping、辅助均衡损失和 expert bias 更新。这些分支显示“MoE”并非一个固定算法；某功能存在也不代表所有模型都启用它。[Megatron MoE routing 实现](https://github.com/NVIDIA/Megatron-LM/blob/c9b53d0a87cb926f47115259593ecfeb351ca29f/megatron/core/transformer/moe/router.py#L750-L841)

【综合设计】在目标硬件上观察 tokens/expert 分布、丢弃比例、专家通信时间、吞吐尾部与显存峰值。Dropless 消除了某类丢弃，不会自动消除负载不均和通信开销。GQA 等注意力设计会改变训练和推理资源需求；全注意力在长序列上的计算项也不能被简单的 `6ND` 覆盖。位置编码、归一化、稀疏注意力或混合结构应以完整候选配方进行验证，不能依据单个内核 benchmark 推导最终质量。

**权衡与故障信号：**理论 FLOPs 减少但墙钟变慢；少数专家持续过载；训练可运行但 checkpoint 无法可靠导出和部署。**通过条件：**质量、稳定性、实测吞吐和服务约束同时通过；超大模型主跑前已在接近目标形状上检验关键执行路径。

## Gate 5：把 packing、mask 和位置当作训练目标的一部分

**输入：**tokenized 文档、长度分布、上下文策略。**输出：**明确的数据批次结构、有效目标 token 计数规则和边界正确性报告。

【综合设计】Packing 提高利用率，也改变文档之间的关系。必须分别定义：哪些位置可以相互注意；哪些目标参与 loss；位置编号是否重置；文档结束之后的下一个 token 是否作为预测目标。因果 attention mask、文档隔离 mask、padding mask 和 loss mask 并不等价。长样本切段还要说明重叠、截断和跨段上下文如何处理。

【公开事实】OLMo-core 的 `get_labels` 先将 label、attention 和 instance mask 指定的位置设为忽略，再左移 labels，并在末尾补忽略项。这个 helper 本身没有完整定义文档间 attention，也不自动证明跨文档目标处理正确；需要沿 dataloader 与 attention 路径继续核对。[OLMo labels 构造](https://github.com/allenai/OLMo-core/blob/92870a33c3fee060d57c3faec52b0b369ece85a6/src/olmo_core/data/utils.py#L590-L605)

【综合设计】应设计但本次未执行的最小检查包括：单文档与等价 packing 的有效位置 logits/loss 对照；EOS、空文档、全 PAD、长度为一及最后位置检查；改变被屏蔽文档后其他文档输出是否按约定保持不变；单卡与分布式拆分的 loss 归一化对照。训练 token 预算区分输入位置数与实际监督目标数，特别是有 padding、过滤实例和选择性 loss 时。

**权衡与故障信号：**packing 提升吞吐却造成意外跨文档泄漏；loss 很低但忽略比例过高；换 GPU 数量后更新幅度改变。**通过条件：**目标对齐与注意力边界符合规范，批量和 loss 分母计算可复核，分布式切分不改变期望目标。

## Gate 6：主预训练交付的是一条可解释的模型轨迹

**输入：**前述冻结的配方、数据与执行配置。**输出：**带完整状态的 checkpoint 序列、消费数据记录、领域评估曲线和进入下一阶段的候选模型。

【综合设计】主训练从随机初始化开始，登记初始化方法、精度、优化器参数组、调度器、批量和数据消费顺序。运行中的资源变化、数据替换或学习率调整应成为可审计的分支或事件。继续训练时恢复的不只是权重，还包括优化器、调度、随机数和数据位置；对应系统实现见训练基础设施章节。

用全局指标和分领域指标共同判断：总 loss 改善可能掩盖语言或代码能力退化；梯度尖峰可能来自坏样本、数值问题、恢复错误或调度变化，不能默认用降低学习率处理所有情况。定期评估保持协议稳定，诊断集与最终保留集分开。预先指定何时继续、暂停诊断、回滚或提前结束，避免把“已投入很多算力”当作继续理由。

**权衡与故障信号：**重复读数据、吞吐逐步下降、特定来源触发尖峰、数据混合漂移、训练 loss 与关键能力持续背离。**通过条件：**候选 checkpoint 来源完整，关键能力和稳定性达到阶段要求；恢复正确性和推理导出一致性已经在执行流程中验证，而不是等训练完才补做。

## Gate 7：按能力缺口设计 midtraining 与长上下文阶段

**输入：**基础 checkpoint、能力缺口、定向数据池和长文档评估。**输出：**阶段对照、下一阶段配方和可进入 SFT/RL 的基础模型。

【公开事实】OLMo 3 的公开流程明确区分广泛预训练、定向高质量 midtraining、含长文档的 long-context 阶段。其 7B 配方报告如下；这些是该模型的实际公开规模，不是超大模型的推荐资源配额。[OLMo 3 官方阶段与运行表](https://github.com/allenai/OLMo-core/blob/92870a33c3fee060d57c3faec52b0b369ece85a6/src/scripts/official/OLMo3/README.md#L23-L77)

| OLMo 3 7B 阶段 | 公开训练 tokens | 公开 GPU 配置 |
|---|---:|---:|
| 预训练 | 5.93T | 512 H100 |
| Midtraining | 100B | 128 H100 |
| Long-context | 50B | 256 H100 |

【综合设计】Midtraining 可以通过更有针对性的代码、数学、知识和任务形态补足缺口，但应与同预算继续原配方的对照比较，并监测通用能力遗忘。数据比例、学习率、训练时长与是否保留广泛数据需要联合决定。阶段名字没有统一边界；也不能把 checkpoint averaging 或多个阶段当成所有模型必需的步骤。

长上下文要一起考虑长文档供给、位置编码、attention 内核、上下文并行、批量和调度。随机拼接短文档可以提供长度，却不能代替跨章节推理的监督信号。评估同时覆盖短上下文回归、不同长度区间、信息所在位置以及真实多段检索和推理，不能只测一个 needle-in-a-haystack 分数。

【公开事实】SmolLM3 的公开配置从 4K 到 32K 同时改变了 RoPE theta、attention 后端、CP、DP、累积步数、学习率和数据列表。例如 theta 从 50,000 变成 2,000,000，CP 从 1 变成 4。两份配置按 `DP × microbatch × accumulation × sequence length` 计算的名义输入 tokens/update 均为 2,359,296；CP 拆分同一上下文，不能再作为独立样本倍数乘进去。这是静态配置计算，没有运行验证；名义输入量也不保证全部位置参与 loss。[SmolLM3 4K 配置](https://github.com/huggingface/smollm/blob/a041759883ec7152d18fb985ea49be641a0bceef/text/pretraining/smollm3/stage1_8T.yaml#L163-L255)、[32K 续训配置](https://github.com/huggingface/smollm/blob/a041759883ec7152d18fb985ea49be641a0bceef/text/pretraining/smollm3/long_context_4k_to_32k.yaml#L213-L298)

**权衡与故障信号：**目标领域提升但通用能力下降；支持更长位置却无法利用远处信息；长序列不稳定；延长上下文后实际 tokens/update 或 loss 分母意外变化。**通过条件：**相对基础 checkpoint 和预算匹配的对照产生可接受收益，短长能力均符合目标，推理端支持相同位置与注意力语义。
