# Claude Code harness 专题：从公开接口到可验证状态机

日期：2026-09-08。目标是理解模型之外的运行机制怎样影响可靠性、成本与可学习轨迹。本专题结合官方资料和课程原创 CPU 实验；它不是 Claude Code 完整内部实现的复刻，也不以泄露镜像作为必读材料。

## 1. 学习位置与证据边界

建议在 [M12：任务、harness、verifier 与 trajectory](../curriculum/03-posttraining-and-agents.md#m12) 后学习，并回访 [M09：推理 Serving 与 Rollout 成本](../curriculum/02-training-systems.md)。先能区分模型请求、工具执行、环境状态和评分证据，再讨论会话恢复；先能区分 token 成本与端到端延迟，再比较 harness 效率。若要把轨迹接入 RL，还需完成 M11 的同步更新基础。

配合 [Claude Agent SDK 仓库笔记](../notes/repositories/claude-agent-sdk.md)，为每项结论标记三类证据：**公开可观察**，指官方文档、固定版本 SDK 源码或实际记录到的接口行为；**阅读推断**，指从证据提出但尚需实验验证的设计解释；**未验证内部实现**，指完整 CLI 内部算法、未公开服务端逻辑或未经认证的泄露内容。官方声明与本地实测也要分列，不能因为文档提供某能力，就写成此次已经运行过。

公开 SDK 可供阅读接口、消息处理和控制回调。其 README 说明发行包下载并捆绑 Claude Code CLI；因此，SDK 源码可读不等于完整核心 harness 已公开。源码、文档和程序包均需记录版本；网页更新不能替代固定快照。

## 2. 官方阅读顺序

1. [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)：画出提示、模型响应、工具结果和结束消息的顺序，再定位权限、预算、压缩与会话章节。先理解公开契约，再追具体参数。
2. [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：比较按需检索、压缩、持久笔记与子 agent；写下每种方法保留和丢失的信息。
3. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：追初始化、功能清单、进度文件、Git 历史与端到端测试怎样支持跨会话工作。文章给出一种实验方案，不是所有任务的通用最优配方。
4. [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)：研究生成与评估分离、明确完成条件，以及随模型变化重新检查 harness 复杂度的必要性。
5. [Claude Agent SDK for Python](https://github.com/anthropics/claude-agent-sdk-python)：最后阅读 `query`、client、消息类型、hook 与 CLI 连接边界。把 SDK 包与被捆绑的执行程序画成两个框，避免将接口代码当作全部内部实现。

## 3. 六个学习主题

### 3.1 Agent loop：谁决定，谁执行，何时停止

官方循环由模型提出响应或工具调用，再由运行程序执行工具并反馈结果，直到结束。阅读时区分一次模型请求、一轮工具交互和整个用户任务；这些计数不能随意互换。练习画出正常结束、工具拒绝、预算耗尽和运行异常四条分支。某次模型声称“完成”只说明循环产生了结束输出，任务是否完成仍要由外部验收判定。

### 3.2 Context：可见上下文不等于完整历史

官方资料讨论按需加载、压缩、结构化笔记及子 agent 隔离。把“存储中存在什么”和“本次请求实际传入什么”分成两列。压缩释放空间，同时可能丢掉后续需要的细节；笔记和检索则引入选择与更新责任。必须记录压缩前后可见内容，不能仅凭最终回答猜测模型读到了哪些材料。具体阈值、保留策略和隐藏提示不从概念文章反推。

### 3.3 Tools and permissions：授权判断先于副作用

官方 SDK 提供工具权限与生命周期 hooks 等控制接口。本专题关注执行边界：模型提出请求后，谁验证输入、谁作出权限决定、何时允许修改环境？检查拒绝是否成为可审计事件，并验证被拒绝操作没有造成副作用。提示中的“请勿写入”不能替代工具执行前的约束；记录允许理由也不能证明操作本身安全。

### 3.4 Sessions：恢复记录不等于证明执行结果

官方文档提供会话延续、恢复和分叉的接口语义。课程另提出一个恢复问题：日志已写入“开始”，进程随后退出，外部效果究竟发生了吗？缺少完成记录可能对应未执行，也可能对应已执行但未记账。这个未知状态不能自动当作失败并重复有副作用的动作。需要检查实际产物、可靠的操作标识或人工核对；这些是本实验的设计要求，不是对 Claude 内部恢复算法的描述。

### 3.5 Subagents：隔离上下文与汇总信息的代价

官方资料将子 agent 作为独立上下文执行任务的一种方式。画出父任务、子任务、返回摘要和共享工作区的边界；上下文分开不代表文件系统自然隔离。设计一个比较：主 agent 读取全部过程，或只接收子任务摘要，哪种更省上下文，哪种更容易漏掉关键证据？记录汇总损失和重复工作，不预先假定多 agent 必然提高成功率。

### 3.6 Evaluation：完成声明要由证据支持

长任务文章强调功能清单、增量进展和端到端测试；后续文章探索独立评估角色。课程据此要求把运行状态、产物是否正确及评分过程是否成功分开报告。固定任务、权限、预算和初始环境后再比较方案，同时保留失败轨迹。评分器报错不能静默计为答案错误；多花工具调用得到更高分，也不能直接解释为模型能力提升。

## 4. 原创 CPU 实验：可审计的 harness 状态机

从仓库根目录运行课程实现：

```bash
python experiments/harness-state-machine/run.py
```

具体输入、输出路径与执行记录见 [实验说明](../experiments/harness-state-machine/README.md)。实验使用确定性的 mock provider 和内存状态，不调用 Claude、不安装官方 SDK、不需要 API key 或 GPU。它验证课程提出的状态机契约；通过这些检查不代表已经复现真实模型行为。

按以下顺序阅读场景、运行程序并检查产物：

1. **拒绝没有副作用。** mock 请求一次写入，权限层拒绝。比较前后的文件内容或操作计数，并检查拒绝事件。只有终端显示“拒绝”而文件已经改变，应判失败。
2. **工具循环有上限。** mock 连续要求工具。给出最多允许的工具循环数，检查实际执行不越界、停止原因可区分。报告这里采用的计数定义；本练习的定义不冒充 SDK 的全部预算语义。
3. **压缩损失必须显式呈现。** 放入一条独特事实，让简化摘要有意遗漏它；比较压缩前后实际传给 mock 的上下文。明确指出保留了什么、丢失了什么，以及哪条后续任务因此缺少证据。用字符或消息计数作简化度量，不声称得到真实 tokenizer 成本或模型正确率。
4. **中断后保留结果未知。** 记录操作开始，并在副作用与完成记账之间模拟中断。恢复时，只有开始而无完成的 journal 项应进入待核对状态，不能自动重复写入。再讨论“副作用前中断”为什么也可能留下相同日志；单看 journal 无法证明两者是哪一种。

先预测每个场景的状态转移，再对照实际 trace。修改一次权限或预算，写出预期改变的检查及理由。恢复实验要分别回答“看见了什么证据”和“据此获准做什么”；不要把读取会话记录本身当作具备 exactly-once 保证。

## 5. 与其他项目的连接

| 比较对象 | 应追踪的共同问题 | 本专题的边界 |
|---|---|---|
| [Pi](../notes/repositories/pi.md) | 上下文变换、模型可见投影、工具与事件顺序 | 比较接口和轨迹；不假设共享 runtime。 |
| [DeepSeek Harness](../notes/repositories/deepseek-harness.md) | 请求如何由日志重建，实时事件与持久记录怎样区分 | 重建请求不自动证明外部副作用结果已知。 |
| [Harbor](../notes/repositories/harbor.md) | 产物收集、独立验证、任务失败与评分故障分类 | 一个 harness 的完成消息不能替代独立 verifier。 |
| [APEX / SkyRL recipe](../notes/repositories/apex-agents-skyrl-recipe.md) | 交互如何转成实际 token、logprob、mask 和 reward | mock 聊天日志不是 RL 样本；压缩或分叉后尤其不能靠重新 tokenize 文本补造采样概率。 |

这些是概念对应，不主张 Claude Code 与上述项目存在直接软件依赖。进一步接 RL 时，应独立证明模型版本、实际采样 token、行为概率和训练 mask 的来源；本 CPU 实验不执行权重更新。

## 6. 交付物与退出标准

交付一张状态转移图、一份“主张—来源—版本—证据等级”表、四个场景的原始日志和检查结果，以及一页跨项目比较。保留运行命令、Python 版本、实际执行日期和未执行部分；输出文件名以实验说明为准。

完成标准：能从一次工具请求追到权限决定、环境变化和终止原因；能展示压缩丢失的具体事实；能解释不完整 journal 为什么留下未知结果，并证明恢复没有自动重复副作用；能指出 mock 没有测量的模型能力。四项检查通过且证据可复查后，再进入真实 SDK 实验。若检查失败，交付失败轨迹与修复解释，不能改写预期结果掩盖问题。

## 7. 可选扩展：真实 SDK、推理与训练

付费 SDK/API 扩展可在隔离的临时项目中重做无害任务，固定 SDK、CLI、模型、权限和预算，保存真实消息与费用；CPU fixture 的确定性断言需要按真实接口重新设计。这部分为可选且未执行，不预填成功率、成本或运行结果。

GPU 扩展可以用可控本地模型替换 mock，研究工具选择与摘要损失；它比较的是另一个模型与自建 harness，不构成 Claude Code 复现。继续做 RL 则返回 M11/M12 的 token 与更新契约，并加入独立评估。先完成一个可反驳、可复查的问题，再扩大模型、任务和并发规模。
